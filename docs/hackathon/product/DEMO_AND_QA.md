# 90秒演示与评委问答

这是一份目标脚本。当前未有本任务实机端到端证据，不能直接宣称已做到。上台前按矩阵逐项标真实/模拟/不可演示；没有真设备ack时不得把网页动画称作硬件闭环。

## 90秒脚本

| 时间 | 我说的话 | 必须可见的实际动作/证据 |
|---|---|---|
| 0–12秒 | “我同时开着三个AI项目。现在要收工，最难的不是再生成一点，而是决定今天到哪儿就够了。” | 预先准备的虚构三个输入，标演示样例 |
| 12–26秒 | “我给它三个输入和12分钟。它只提出一个今天能完成的动作，另外两项停在这里。我确认后，它才成为承诺。” | 真AI候选和确认；若预录标预录，若规则标规则兜底。不得假装现场推理 |
| 26–37秒 | “这一条现在交给手里的设备。这里显示的已接收，来自设备保存后的回执。” | 主机pending→ack，设备显示同一动作/版本；断线时不伪装成功 |
| 37–50秒 | “我可以一直按、一直转。它给手真实的机械反馈，但不会把把玩当作完成。” | 真机械全行程，计数保持不变；原件未装就展示分体并明确说明 |
| 50–64秒 | “这一步做完，我明确确认。听到两声，代表设备已经保存，不需要再打开任务列表。” | 演示任务设成现场可完成的小动作；实体二次确认，屏幕与两短音；拔开通信后重复不加计数 |
| 64–77秒 | “没做完也能停。我封存的是下一次从哪儿开始，不是谎报今天完成。” | 使用预置第二个未完成样例，常驻“场景切换”；封存音与未完成标记；不要暗中重置同一个周期 |
| 77–90秒 | “现在演示时间前进到明天，接回昨天这一件事。我们接下来验证：它是否真的比玩具加快捷键更少让人回屏；如果没有，就不值得做成硬件。” | DEMO TIME常驻；恢复同一已存卡；展示价值试验设计，不伪造结果 |

正式90秒可提前录制跑通一次并计时。云调用超过预算时主动切换标明的录屏/规则模式；90秒脚本含两个场景，不能将预置状态切换剪成连续成功。若现场只有一个场景，优先保留未完成→封存→次日恢复，完成操作展示为短补充。

## 评委问答

**为什么需要硬件？** 目前是待验证的产品假设。它把真实机械把玩、离桌后的明确提交和本地状态放在同一件物品中。若玩具加快捷键一样好，我们不会用“仪式感”替失败辩护。

**为什么不是键盘宏或鼠标快捷键？** 坐在电脑前它们可能更快，我们保留这个对照。候选优势只在离开键鼠、仍想收尾且不再进入工作界面的场景；要用回屏次数和错误提交验证。

**手机App不也随身？** 能，而且是强替代。需要比较取出、解锁、确认的实际步骤和误触，不假定所有人都被手机分心。手机同样好就没有硬件必要性。

**普通玩具不就够了？** 对单纯把玩够了。本产品额外记录确认后的单一承诺并给出保存结果；仍需与玩具+快捷键组合比较，不能只赢一个被削弱的对照。

**AI在哪里，为什么不用普通表单？** AI只用于把多项冲突输入压缩成一个可验证动作并解释停车项。执行与封存是确定性本地状态机。若表单同样省时、候选频繁被改，AI也应降级，不能为有AI而增加对话。

**旋转如何联动？** 当前不检测。旋转/按压原件负责被动触感，KEY1/KEY2明确提交。没有Hall/编码器就不编造转动数据。随机把玩和正式承诺分开是有意设计。

**反馈是不是震动？完全离屏吗？** 当前是屏幕及可选音码，没有内置触觉马达。声音可在不看屏时确认完成/封存，任务全文、编辑及静音状态需要看设备或回主机。不能宣传全流程无屏。

**真的让用户停止工作吗？** 只确认封存、保留恢复入口；当前不拦截其他软件。行为改变是实验目标，不是已经证明的疗效或强制约束。

**为什么选这个模型？** 按压旋转款最接近持续把玩，但目前静止底座、全行程与装机都没验证；它是优先试验对象，不是已经可用的整机。其他两款同样有尺寸或保持力阻塞。

**成本、续航、上市时间？** 当前BOM以现成板和打印件建立，尚无整机报价/续航数据。没有人员和截止时间就只分资源档，不作量产承诺。
